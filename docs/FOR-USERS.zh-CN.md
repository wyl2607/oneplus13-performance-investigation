# 写给 OnePlus 13 机主 —— 为什么你的跑分只有该有的一半

如果你给 OnePlus 13 跑过分，得到的数字远低于同一款手机在别处的成绩，这份文档解释发生了什么、怎么用两条命令自己查，以及你有哪些选择。

本文针对 OnePlus 13（CPH2653/CPH2655，骁龙 8 至尊版 / SM8750），但机制是一个 OPLUS 内核模块，所以其他一加和 OPPO 设备也很可能带着它。**如果你测了一台，请开 issue —— 见 [需要帮助](#需要帮助)。**

---

## 先说结论

你的手机有两颗快的「超大核」（CPU6 和 CPU7，额定 4.32 GHz），以及六颗较慢的核（CPU0–CPU5，3.53 GHz）。

一个叫 **`oplus_bsp_task_overload`** 的 OPLUS 内核模块会盯着在超大核上持续忙碌的线程。发现之后，它判定这条线程「异常」，并压低调度器被允许认为这条线程需要的 CPU 量。这个上限低到线程现在能轻松塞进一颗 *中核* —— 于是 Linux 的调度器完全按设计工作，把它挪过去，然后就放在那里。

结果是：**你的跑分跑在慢核上，两颗快核在一旁空转。**

在参考机上，只把这个上限抬回去 —— 其他什么都不改 —— Geekbench 7 单核从 **934 变成 2126**，跑分占用超大核的时间从 **8% 变成 59.5%**。

### 它 *不是* 什么

每个去查的人都会在这里栽跟头，因为所有常规诊断看起来都完全健康：

| 你会去看的东西 | 它显示的 |
|---|---|
| CPU 温度 | 40–50 °C。触发点是 105 °C。 |
| `Thermal Status` | 整场都是 `0`（NONE） |
| 温控冷却设备 | 全部 20 个都是 `cur_state=0` |
| `scaling_cur_freq` | 正常 |
| `scaling_max_freq` | 没有被压低 |
| cpuset / 亲和性 | `top-app`，8 颗 CPU 都允许 |
| 调速器 | `walt`，正常 |

**这不是温控降频，你的手机也没有坏。** 按额定频率等比换算，参考机在解除上限之后测出来比一台健康对照机 *略快一点*。

问题唯一能看见的地方，是一份按线程记录的调度器文件，主流工具都不会去读。

## 自己查

读取其他进程的调度状态 **需要 root**。没有 root 看不到。

手机用 ADB 连上，跑一项跑分或任何持续 CPU 任务，并在它运行时：

```sh
adb shell su -c 'cat /proc/task_overload/abnormal_task'
```

如果模块存在并且已经动手过，你会得到一张这样的表：

```
pid    uid    limit_flag  comm             date           temp  freq
26298  10xxx  466         pool-5-thread-1  1786639362457  0     3283200
```

`limit_flag` 就是那个上限。**`1024` 表示没动过。任何更低的值都是被钳制的线程。**

要确认它确实写在线程上，把 `<pkg>` 换成你在测的应用：

```sh
adb shell su -c 'grep -H "uclamp.max" /proc/$(pidof <pkg>)/task/*/sched'
```

健康线程读出来是 `uclamp.max : 1024`。被钳制的读出来是 `limit_flag` 的值。

### 这些数字是什么意思

这个上限不是常数。它是按你的线程被判定那一刻，超大核集群碰巧处在的时钟算出来的：

```
limit_flag = floor(0.6 × 1024 × prime_current_freq / 4320000)
```

于是这条线程只剩下它当时所用性能的 60%。而超大核时钟是会变的，**上限也会变** —— 所以同一台手机反复跑分会得到天差地别的分数。参考机上三次是 934、1145、1229，对应上限 346、466 和 466。这是 31% 的波幅，不是噪声。

**如果你一直在用单次跑分数字去比不同的一加设备，你比的是一个分布里的抽样，不是测量值。**

## 什么会触发它

用受控忙循环测过：

- **只针对应用进程。** 同样的负载以 `root` 或 `system` 身份跑，会被写进表里但 `limit_flag = 1024`，实际上从未被钳制。只有普通应用 UID 会被压。（这也意味着你从 root shell 跑的跑分 *不会* 复现这个问题。）
- **只有线程在超大核上时。** 钉在 CPU0–5 的循环 45 秒内从未被钳制。同样的循环钉在 CPU6–7，5.1 秒就被钳制。
- **几秒之内。** 六次试验：五次在 6 秒内被钳制，一次在 27 秒。

合在一起，这是一道单向棘轮：

```
your thread gets busy
  -> the scheduler correctly promotes it to a prime core
  -> the guard sees it there and caps it
  -> the thread falls back to a mid core
  -> on a mid core it can never trigger again, so it never gets promoted back
```

它惩罚的恰恰是调度器判断正确的那些线程，而且没有回头路。

### 现实里影响什么

任何让一条线程忙碌超过几秒的事情：

- 跑分
- 视频导出和转码
- 大图修图
- 代码编译
- 模拟器
- 端侧模型推理
- 大压缩包解压

**启动应用不受影响** —— 冷启动在 0.5–2 s 内结束，防护还没介入。这和测到的另一件事一致：去掉 *另一道* OPLUS 限频器，启动时间也没有任何变化。日常跟手程度确实没问题。你付出代价的，恰恰是又长又重的单线程活 —— 也正是你会注意到的那种活。

## 这个模块为什么存在

值得公平地说一句。

当上限被抬起、跑分真正用上超大核时，参考机的 CPU 结温跑到 **87 °C（95 分位），峰值 95 °C** —— 而手机外壳几乎只动了一度，从 35.0 到 36.1 °C。

Android 的温控框架按 *外壳* 温度升级，不是按结温。所以一条真正失控的线程可以在这颗 SoC 内部无限期地待在 87 °C，手机摸起来永远不热，`Thermal Status` 永远不会离开 0，系统里没有任何东西会介入。在一台密封、被动散热的设备上，这是一个真正的问题，针对它做一道防护是站得住脚的设计决定。

防护做不到的是：把失控 bug 和用户主动要求的持续计算区分开。两种情况它看到的是同一件事：一条钉在快核上 100% 的线程。

## 你能怎么做

**这个项目给不出一个可以当一键开关递给你的安全修复，对任何声称能给的人都应该保持怀疑。**

做出 +128% 那个结果的干预，是一个用 Android 自带的 `uclampset` 工具把 `uclamp.max` 重置回 1024 的循环，每 250 ms 一次：

```sh
uclampset -a -M 1024 -p <pid>
```

这份构建里 `uclampset` 在 `/system/bin/uclampset`。改动不持久 —— 进程一死就没了，重启也没了。它不动别的：不改 CPU 频率上限，不改 cpuset，不改温控配置，不改调速器，不改内核模块参数。

但动手之前，把上面的温度数字再读一遍。那次实验里，我们自己的安全防护在 **98.4 °C** 中止了运行，距硬件触发点只剩 6.6 °C。无人值守跑、大热天跑、或者套着壳跑，和盯着跑一次跑分，完全不是一回事。

如果你要在这上面做东西，说得通的设计 **不是**「关掉防护」：

1. **按应用白名单** —— 只豁免用户明确选中的应用，绝不全局。
2. **你自己的温控** —— 结温到阈值就退回原厂行为。我们的在 95 °C 正确触发，大概十行 shell。
3. **时间上限** —— 只在一段有限窗口里允许满性能，然后退回去，免得一个被忘了关的应用把设备烤熟。

这里每一项测量用到的工具都在本仓库里，除明确注明外都是只读的。

## 需要帮助

整次调查是 **一台设备、一项跑分、一对 A/B**。别人能贡献的最有用的东西，是另一台手机的一个数据点。

如果你有一台已 root 的一加或 OPPO，请跑：

```sh
adb shell su -c 'ls /proc/task_overload/ 2>/dev/null && cat /proc/task_overload/abnormal_task'
adb shell su -c 'grep -c oplus_bsp_task_overload /proc/modules'
adb shell su -c 'cat /sys/devices/system/cpu/cpu*/cpu_capacity'
```

然后把输出、型号和构建号开成 issue。特别有用的是：

- **你的设备上到底有没有这个模块？** 这决定了它是 OnePlus 13 的特例，还是 OPLUS 范围的行为。
- **`0.6` 这个系数还成立吗？** 公式是用一台设备上的四个观测点拟合的。
- **一份 `abnormal_task` 里没有被钳制行的设备上的 Geekbench 7 成绩**，这会补上本项目目前缺少的对照。

如果你不想公开装了哪些应用，请打码 10000 以上的 UID —— 分析只需要区分「应用」和「root/system」。
