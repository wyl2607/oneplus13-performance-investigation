# OnePlus 13 —— 性能调查

一份基于实测的调查：OnePlus 13 / 骁龙 8 至尊版（SM8750）的持续 CPU 性能为什么会异常偏低。涉及 OPLUS 的 `task_overload`、`uclamp.max`、调度器核心分配、`cpufreq_bouncing`，以及热行为。

这里的每一个数字都是通过 ADB 在真机上测出来的，没有推算值。走过的弯路也一并保留。

---

## 我的 OnePlus 13 坏了吗？

**几乎可以肯定没有。** 硬件没问题。调度器被告知：你的任务并不需要那些快核。

这台手机有两颗超大核（CPU6/CPU7，4.32 GHz）和六颗中核（CPU0–5，3.53 GHz）。一个 OPLUS 内核模块 **`oplus_bsp_task_overload`** 会盯着那些在超大核上持续忙碌的应用线程，判定它们「异常」，然后把 `uclamp.max` 压下去 —— 调度器正是用这个值来判断一个任务需要多少 CPU。这个上限低到任务刚好能塞进一颗中核，于是 Linux 按设计把它挪过去，并且再也没有理由把它搬回来。

在参考机上，**只**把这个上限抬回去，其他什么都不改：

| | 原厂 | 解除 uclamp 钳制 |
|---|---|---|
| Geekbench 7 单核 | 934 | **2126** |
| Geekbench 7 多核 | 6017 | **8386** |
| 跑分占用超大核的时间 | 8.0% | **59.5%** |

按额定频率等比换算后，这台设备测出来比一台健康对照机 *略快一点*。没有东西坏掉，也不需要刷机。

**这不是温控。** 钳制状态下跑分时，CPU 温度只有 40–50 °C，触发点是 105 °C，`Thermal Status` 一直是 `0`，全部 20 个冷却设备读数都是 `cur_state=0`。

**影响什么、不影响什么** —— 测过的标明测过，没测的标明没测：

| 负载 | 受影响？ |
|---|---|
| 启动应用、界面、滑动、短突发 | **否** —— 冷启动在防护介入之前就结束了（已测） |
| 跑分 | **是** —— 最容易复现的场景，所以最先在这里被发现 |
| 视频导出、编译、模拟器、端侧推理 | **预期会** —— 负载形态与复现场景相同，*尚未测量* |
| 游戏 | **未知** —— OPLUS 把游戏走单独的 `game_opt` 路径；未测试 |

Geekbench 既不是问题本身，也不是针对目标。它只是触发厂商调度策略最干净的方式，而这套策略同样作用于真实的持续负载。

## 我能自己检查手机吗？

可以，只读，需要 root（读取其他进程的调度状态是特权操作）：

```sh
adb push tools/diagnose.sh /data/local/tmp/
adb shell su -c 'sh /data/local/tmp/diagnose.sh <package>'
```

**在应用处于持续 CPU 负载时**运行。它什么都不写 —— 只读 `/proc` 和 `/sys`，把看到的东西打出来，包括你的设备上到底有没有这个模块。如何解读输出见 [docs/FOR-USERS.zh-CN.md](docs/FOR-USERS.zh-CN.md)。

**欢迎贡献一份结果**，尤其是非 OnePlus 13 的 OPLUS 设备 —— 这个项目目前最大的缺口就是样本只有一台机。

## 怎么修？

先看 [`mitigation/`](mitigation/) —— 而且先读热警告。

诊断是只读的、安全的。缓解手段不是。解除钳制后，CPU 结温跑到 **87 °C p95，峰值 95 °C**，而手机外壳只从 35.0 升到 36.1 °C。Android 的温控框架按 *外壳* 温度升级，所以系统里没有任何东西会介入。**你的手感觉不到。**

这也是 *支持* 这个模块存在的诚实理由：一条真正失控的线程可以在这颗 SoC 内部无限期地待在 87 °C，而手机摸起来永远不热。防护做不到的是：把失控 bug 和用户主动要求的持续计算区分开。

所以这个项目不会提供一键「解锁全部性能」开关，你也应该对任何声称能这么做的东西保持警惕。

# 写给研究者

本文其余部分是技术记录。

## TL;DR —— 最初的 CFB 发现，至今仍然成立

一个叫 **`cpufreq_bouncing`**（CFB）的 OPLUS 内核模块，会在持续负载 **50 ms** 之后通过 `freq_qos` 钳制 CPU：

| 集群 | CPU | 硬件上限 | CFB `limit_freq` | 比例 |
|---|---|---|---|---|
| `policy0`（中核） | 0–5 | 3 532 800 | **2 400 000** | 68% |
| `policy6`（超大核） | 6–7 | 4 320 000 | **2 438 400** | **56.4%** |

这 *不是* 温控降频。它在结温约 50 °C 时就会介入，此时 Android 温控框架报告 `Thermal Status: 0`，每个 CPU 冷却设备都是 `cur_state=0`。

因为 CFB 通过 `freq_qos` 生效，而 cpufreq 取所有 QoS 请求的 **最小值**，以 root 写入 `scaling_max_freq` 没有任何效果 —— 诊断时非常容易因此误判。

> **这套调校测到的 +30%，其作用机制可能是本仓库当时完全不知道的。**
> 钳制值是 `floor(0.6 × 1024 × prime_cur_freq / 4 320 000)`。原厂状态下，CFB 把超大核集群按在 2 438 400，对应钳制值 346。调校后，上限把它按在 3 283 200，对应 466。这个比值是 **+34.7%**，对照测到的调校增益 **+30.3%** —— 比当时以为起作用的中核上限变化（+21.6%）更贴。负载从未跑在超大核上，但超大核的时钟决定了它被允许使用中核的多少。尚未证实；与目前每一个数字都吻合。

## 往下读之前先看这段：解除钳制实际值多少

解除钳制的收益是 **+30% 单核（Geekbench 7）**，可复现到 2.4% 以内。目前测过的其他所有场景都 **完全没有收益**。

| 场景 | 收益 | 依据 |
|---|---|---|
| Geekbench 7 单核 | **+30%**（947 → 1234） | 三次运行，波幅 2.4% |
| Geekbench 7 多核 | +19%（5222 → 6218） | 三次运行，波幅 11.5% |
| *（这两个数字都不是健康基线 —— 见下文更正）* | | |
| **应用冷启动** | **无** | 设置 265 vs 276 ms，地图 200 vs 203 ms —— 在噪声范围内 |
| **持续全核** | **无** | 落地频率由温控环路决定，不是由上限决定 |
| **GPU 受限负载** | **无** | GPU 负载期间超大核空闲在 1 017 600；从未接近上限 |
| Geekbench 7 OpenCL | −0.68% | 噪声 |

「启动应用 *理应* 受益」这个推理是通顺的，但是错的。CFB 的阈值是 50 ms，冷启动是 500–2000 ms 的密集 CPU 工作，所以限频器一定会介入 —— 它只是不是瓶颈。冷启动由 I/O、zygote fork、类加载和 binder 主导，而且很大一部分跑在中核上，而不是被重钳制的超大核上。

**对这套调校诚实的描述是：它解除了厂商对持续单线程计算的钳制。** 这覆盖跑分，也说得通会覆盖视频导出、照片处理、模拟和编译 —— 这些都还没测过。它不是通用的「性能模式」，手机的日常跟手程度不会变。

整次调查里测到的最大杠杆根本不是 CPU 调校 —— 而是 **主动散热**，值 +44% 持续频率（15 分钟全核负载），因为 Android 温控框架按外壳温度而不是结温来管控。见 [DATA.md 第 18 节](docs/DATA.md)。

## 根因

原厂 `/sys/module/cpufreq_bouncing/parameters/config`：

```
clus 0 first_cpu 0 ctl 1        clus 1 first_cpu 6 ctl 1
limit_freq: 2400000             limit_freq: 2438400
limit_level: 10                 limit_level: 6
limit_thres: 50 ms              limit_thres: 50 ms
max_freq: 3532800 15            max_freq: 4320000 15
cur_level: 15                   cur_level: 15

global: enable=1  freq_qos_check=Y  decay=80  sleep_range_ms=20,30
```

`limit_level` 是集群 OPP 表的下标。对 `policy6`：

```
idx    0       1       2       3       4       5       6  <-- limit_level
kHz  1017600 1209600 1401600 1689600 1958400 2246400 2438400 ...  4320000 (idx 15)
```

持续负载下，测到的钳制与 `limit_freq` **精确到 kHz 完全一致**：

```
Screen ON, single thread pinned to cpu7, stock config
 t+0s  cur=1017600  max=4320000
 t+1s  cur=2438400  max=2438400   <-- clamped within 1 s
 ...
 t+16s cur=2438400  max=2438400
```

### 内核堆栈追踪证据

`/proc/oplus_freqreq_monitor/fqm_dump` 记录每一次 `freq_qos` 请求及其调用栈：

```
req, idx, ts, cluster, pid, ..., max, ..., comm, utc, stack
41848, 18, 1858888, 1, 136, 0, 2438400, 0, 2438400, 1, kworker/5:1H, ...,
   freq_qos_update_request<-cb_do_boundary_change_work [cpufreq_bouncing]<-process_scheduled_works
```

设 `enable=0` 会正确地通过 `enable_store [cpufreq_bouncing]` 释放请求（`max` → `2147483647`）。

### CFB 是至少五个 `freq_qos` 请求方之一

空闲状态下抓 5 秒 `fqm_dump`，已经能看到五个不同来源在争同一个 `min()`。关掉 CFB 只会去掉其中恰好一个：

| `comm` | 内核模块 | 角色 |
|---|---|---|
| `UrccWorker` | `msm_performance` | 亮/灭屏电源策略（正常，见 METHODOLOGY 陷阱 2） |
| `gameSceneLooper` | `oplus_bsp_game_opt` | OPLUS 游戏优化器 —— **此前未刻画** |
| `thermal-engine-` | `qti_cpufreq_cdev` | Android/QTI 温控冷却设备 |
| `kworker/N:1H` | `cpufreq_bouncing` | 本仓库记录的那道钳制 |
| — | `sched_walt` | WALT 调速器 |

`/proc/game_opt` 暴露游戏优化器的控制项，包括 `cpu_max_freq`（空闲时读到 `2147483647` = 未封顶）、`dsu_freq`、`disable_cpufreq_limit`、`skip_gameself_setaffinity`，以及一个名叫 **`fake_cpu7_cpuinfo_max_freq`** 的节点，作用是伪造 CPU7 对外宣称的上限。本机读数为 `0`，所以本仓库通篇引用的 `4 320 000` 是真值，不是合成出来的。

另外，cpuset `oiface_fg` 的 `cpus=3-6` —— **CPU7 被排除在外**，而 `oiface_fg+` 是 `cpus=3-7`。跑分线程会不会被放进 `oiface_fg` 尚未测试，也是上文残差的候选解释之一。

## 已排除

| 假说 | 结论 | 证据 |
|---|---|---|
| 温控降频 | **否** | `Thermal Status: 0`；全部 20 个 CPU 冷却设备 `cur_state=0`；钳制在 50 °C 就生效，对照 105 °C 触发点 |
| OPP 表永久损坏 | **否** | `time_in_state` 显示自开机起 4 320 000 的驻留时间在累积 |
| Magisk / LSPosed 模块 | **否** | 两道限频器都是原厂 OPLUS 内核/厂商组件 |
| `UrccWorker` / `msm_performance` 封顶 | **否 —— 正常** | 1 996 800 / 2 649 600 的封顶是 **灭屏** 电源策略。亮屏后回到硬件满额。见 METHODOLOGY.md |
| 搞砸的国行→OOS 转换 | **否** | `boot`、`vendor`、`odm` 的 fingerprint 都是同一增量；`my_product`（2.6 GB）正确填充了 EEA 内容；设备树和任何厂商配置里都没有 CFB 引用 |

最后一行很重要：**重刷同一套 OOS 构建改不了这件事。** CFB 默认值编译进了内核模块，模块打在 `boot` 镜像里，而这张镜像的 fingerprint 已经和 `vendor`、`odm` 完全一致。

## 热特性

最坏情况：纯 ALU 的 shell 忙循环（比 Geekbench 更热）。结温传感器是 `thermal_zone28`（`cpu-1-1-1` = cpu7）。硬件触发点是 105 °C。

### 单线程钉在 cpu7

| `scaling_max_freq` 上限 | 稳态结温 | 峰值 | 外壳 | 距 105 °C 余量 |
|---|---|---|---|---|
| 2 438 400（原厂 CFB） | 51 °C | — | 31 °C | 54 °C |
| 2 841 600 | 62 °C | 64 °C | 33 °C | 43 °C |
| **3 283 200** | **73 °C** | 74 °C | 33 °C | **32 °C** |
| 3 513 600 | 80 °C | 82 °C | 33 °C | 25 °C |
| 无限制（CFB 关） | 平均约 88 °C，振荡 | 101 °C | 32 °C | 4 °C |

CFB 关掉且没有上限时，`scaling_max_freq` 会在 3 283 200 和 4 320 000 之间自行调节 —— 高通 LMH/DCVS 环路仍在工作，把核心按在触发点以下。关掉 CFB **不会**让 SoC 失去保护。

### 全核（8 线程），40 s

| 上限（p0 / p6） | 落地频率 | 40 s 时结温 | 外壳 | 结果 |
|---|---|---|---|---|
| 2 918 400 / 3 283 200 | p6 → 2 841 600 | 89 °C | 34 °C | 未中止，`Thermal Status: 0` |
| 2 745 600 / 3 072 000 | p6 → 2 841 600 | 89 °C | 35 °C | 未中止，`Thermal Status: 0` |

**两种配置在 40 s 时收敛到同一点。** 全核负载下，落地频率由温控/功耗环路决定，不是由上限决定 —— 所以把上限压到 3 283 200 以下，热上什么都买不到，只损失单线程性能。

> **这组 40 s 数字是瞬态，不是稳态。** 一次 15 分钟运行
> （[DATA.md 第 17 节](docs/DATA.md)）显示超大核集群继续降到
> **1 689 600** —— 低于 CFB 自己的 2 438 400 钳制 —— 同时 Android 温控框架
> 升级到 status 2，结温反而 *更低*，落在 69 °C。本仓库里任何从 40 s 窗口
> 得来的结论，描述的都只是突发行为。

## 缓解

两件事实决定了怎么修：

1. CFB 关掉之后，用户空间写入 `scaling_max_freq` **就会**生效（它变成最小的 QoS 请求）。这样可以给出精确、可预期的上限，不必去反推 CFB 的 `config` 写入格式。
2. **每次亮屏/唤醒，系统都会把 CFB 重新打开。** 已验证：亮屏时它能在 `0` 上待 60 s，灭屏也能保住，一唤醒就翻回 `1`。所以一次性开机脚本不够 —— 需要一个看门狗。

`mitigation/oneplus13_cfb_tune.sh` 实现了这件事。利弊见 [mitigation/README.md](mitigation/README.md) —— 它确实会永久关掉一道厂商限频器，这是一个真正的取舍，不是白捡的便宜。

灭屏省电仍然保留：URCC 的灭屏封顶（1 996 800 / 2 649 600）是另一道更低的 QoS 请求，仍会通过 `min()` 胜出。

### 用 Geekbench 7 验证

一次开机内生效（`cfb_enable=0`，`p0max=2918400`，`p6max=3283200`，亮屏），然后在设备上跑 Geekbench 7：

| | 原厂（4 次） | 调校后 | 变化 |
|---|---|---|---|
| 单核 | 891 / 1052 / 911 / 935（~950） | **1253** | **+32%** |
| 多核 | 5279 / 5344 / 5178 / 5086（~5220） | **5945** | **+14%** |

单核结果在跑之前就只用时钟比预测过：

```
950 × (3 283 200 / 2 438 400) = 950 × 1.347 = 1280   predicted
                                              1253   measured    (2.1% error)
```

对上的是预测的 *量级*，而不只是「变快了」，这才把因果链闭合：根因 → 机制 → 干预 → 定量预测 → 测量。

多核只涨 +14%，与上面的全核测量一致：无论上限多少，LMH 都会把超大核集群拉到 2 841 600；中核跑在 2 745 600–2 918 400，对照原厂 2 400 000，纯时钟缩放预测约 +17%。落到 +14% 的缺口是预期中的 —— 多核比热特性里用的单线程 ALU 循环更受内存和 DSU 约束。

两个数字都是 Geekbench 7，并且只和同一台设备的 Geekbench 7 结果比。见下文更正。

## 未决问题 —— 需要帮助

**1. 谁把 `uclamp.max = 466` 写到跑分工作线程上？** —— *回答残差；见 [DATA.md 第 22 节](docs/DATA.md)*

残差已经对上，不是 IPC。一份 437 s 的追踪显示，Geekbench 单核负载在真正单线程样本里有 95.8% 跑在 **中核** 集群上，两颗超大核空闲在 1 017 600，占其中 97.8% —— 与此同时 `policy6 scaling_max_freq` 纹丝不动地停在 3 283 200，cpuset 是 `/top-app` 且 `cpus_allowed=0-7`，`Thermal Status` 是 `NONE`，每个冷却设备读数都是 0。超大核是空着的，只是根本没用上。

工作线程整场带着 `uclamp.max = effective uclamp.max = 466`，一结束就回到 1024。中核 `cpu_capacity` 是 **792**，超大核是 **1024**，被钳到 466 的任务塞得进一颗中核，调度器没有任何理由把它往上提 —— 同一道钳制还把中核按在自己的上限以下（平均 2 555 MHz，对照可用的 2 918 400）。

**来源已确认：`oplus_bsp_task_overload`。** 该模块导出 `set_uclamp_max`，知道集群拓扑（`golden_cpu`、`goplus_cpu`、`max_cluster_id`），暴露 `/proc/task_overload/skip_goplus_enabled` —— *skip gold-plus*，也就是超大核集群 —— 并在 `/proc/task_overload/abnormal_task` 维护自己的表，列是 `pid uid limit_flag comm date temp freq`。表里有：

```
30423  10xxx  466  pool-5-thread-1  2026-08-13 17:33:55  0  3283200
18846  10xxx  466  pool-7-thread-1  2026-08-13 17:48:50  0  3283200
```

TID 30423 正是追踪里记到 `uclamp.max = 466` 的那条线程。其他行显示普通应用线程上也有 346 / 376 / 436 的钳制，所以这是一道通用的失控线程防护，不是跑分检测。`/proc/oplus_qos_sched/qos_task_uclamp` 全程读空，**与此无关** —— 早先对它的怀疑是错的。

仍未知：触发条件和具体限值怎么选。置信度分级和用于确认的 kprobe 设置见 [DATA.md 第 23 节](docs/DATA.md)。

这一发现也把 `mitigation/` 里超大核上限的地位降了下来：测到的 +30%，最说得通的是 *中核* 从 2 400 000 升到 2 918 400，而不是超大核那对做了什么。

**2. `limit_level 6` 是 CPH2653 的原厂值，还是这台机这个构建特有的？**

这台设备上没有任何东西能回答这个问题。需要另一台 OnePlus 13 的一个数据点。如果你有，请跑 [`tools/collect-report.sh`](tools/collect-report.sh)（只读，不以 root 改任何东西，不含个人身份信息）并把输出开成 issue。

**3. 一份可核验的同版本 GB7 对照。**

2 681 / 8 846 这个支撑问题 1 的数字是用户提供的，无法程序化抓取。另一台 OnePlus 13 的 GB7 成绩，连同 `tools/collect-report.sh` 输出一起交上来，会让问题 1 更扎实。

### 更正，两次 ——「第二因子」回来了，而且是目前主要的未决问题

这一节已经朝两个方向都错过。当前立场：

**几乎可以肯定还存在第二个、非频率的瓶颈。**

第一版用这台设备的 Geekbench **7** 分数去对比 Geekbench **6** 的参考数字来论证存在第二个瓶颈。那个对比无效，论证已撤回。

撤回之后又矫枉过正。它引用 [Signal65 的 GB7 分析](https://signal65.com/research/geekbench-7-analysis-and-early-results/)，指出同一硬件上 GB7 单核分数会低于 GB6 —— 只取了这个效应的 *方向*，从未核对它的 *量级*。Signal65 的成对测量是：

| CPU | GB7 相对 GB6 单核 |
|---|---|
| Snapdragon X2 Elite | −15% |
| Apple M5 | −14% |
| Intel Core Ultra X9 388H | −10% |
| AMD Ryzen AI 9 465 | −9% |

用 9–15% 的重标定去抹掉一个 **2.2 倍的差距**。做不到。把观察到的最大降幅套到 OnePlus 13 大约 3 000 的 GB6 单核上，期望的 GB7 数字大约是 **2 550–2 730**。另外注意，GB7 保留了 GB6 的基线 *分数* 2 500，只换了基线 *机器*（Dell Precision 3460 / i7-12700 → Lenovo Legion / Ryzen 7 7700），所以重标定的幅度从构造上就被框在这个量级。

一份 Geekbench 7.0.0 的 OnePlus 13 CPH2655 成绩 **2 681 / 8 846** 正好落在这个预测区间里。（报告于 `browser.geekbench.com/v7/cpu/116261`；Geekbench Browser 对自动抓取返回 HTTP 403，所以此处按用户提供引用，本仓库未独立核验。）

#### 残差在两种不同上限下几乎恒定

对照 2 681 参考（4 320 000）：

| 状态 | 超大核上限 | 相对额定比 | 时钟比预测 | 实测 | 残差 |
|---|---|---|---|---|---|
| 原厂 CFB | 2 438 400 | 0.564 | 1 513 | 947 | **62.6%** |
| 调校后 | 3 283 200 | 0.760 | 2 038 | 1 234 | **60.6%** |

两种不同钳制水平，残差因子本质上都是约 0.61。不随时钟移动的残差是 **每周期** 损失，不是占空比损失 —— 这指向 DSU/LLC 时钟、DDR，或跑分线程其实并不驻留在超大核上，而不是任何会表现为 `scaling_cur_freq` 偏低的东西。

这也解释了为什么 [DATA.md 第 10 节](docs/DATA.md) 的机内预测能验到 2.1%：一个恒定的乘性因子在比值里会消掉。**比值吻合被误当成了绝对水平吻合。** 两件事同时成立 —— 这台设备内部的时钟缩放是干净的，而绝对水平被别的东西压低了。

#### 对上文数字的后果

`3 283 200` **不是**「满速」，也绝不能这么说。超大核对的 `cpuinfo_max_freq` 是 `4 320 000`，中核是 `3 532 800`，所以这套调校的上限刻意保守在额定的 **76%** 和 **83%**。因此调校后的 1 234 并不是这颗 SoC 的健康基线 —— 它是 76% 时钟上限下的分数，上面还叠着那个未解释的约 0.61 因子。

残差调查用 [DATA.md 第 21 节](docs/DATA.md) 描述的只读追踪工具链跟进。
